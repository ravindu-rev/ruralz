Brief for the user's decision, 2026-10-10. Written from the five research reports of `m1-yaml-decision.js` plus the author's own checks (section 3.5), then revised the same day after an evidence review and a devil's-advocate review. No other repository file was changed.

Every figure marked "(estimate)" is a projection, not a measurement.

## 1. Decision needed

Which parser should `internal/config/profile` use for the restricted YAML 1.2 profile: keep `github.com/goccy/go-yaml` v1.19.2 behind WP-33's guard layer, move to `go.yaml.in/yaml/v4`, or replace both with a parser Ruralz writes for exactly the profile? WP-33 is committed (`086e74d`) with five open confirmed findings that wait on this choice: one verified blocker (the directive-line flow gadget) and four verified majors (the reviewer rated four of the five as blockers). The answer also decides whether ADR-0003 is superseded, which modules stay in `go.mod`, and what the next WP-33 run builds.

### 3.7 Limits of this evidence

- The spike and the v4 prototype have had no adversarial review; WP-33 had four loops. Open-finding counts are therefore not like for like, and C's first review rounds will find defects. The advocate's independent probes found no spike defect, but they are not a review.
- The 224 rows come from goccy findings; the WP-33 differential shares the reused readers with the spike; the generator has the parser's author. Only the suite, the positions against v4 and the 332,561-input differential against v4 and yaml.v3 share neither code nor authorship with C.
- The 32 style rows were chosen to probe corners, so they say which shapes each parser refuses, not how often users write them.
- Production plumbing (`diag.Related`, `MaxDiagnostics`, Yield, ctx, `tree.Node` key positions) is missing from both the spike and the prototype, so their line counts are lower bounds. The spike's converted tree is its own type, not `tree.Node`, so production memory may differ.
- The first WP-33 review's 8 findings were saved only as counts; 5 were reconstructed. Root-cause classes are the history researcher's judgment.
- GitHub REST and MCP access was blocked for the upstream researcher; issue and PR text comes from WebFetch summaries and first-page searches.
- Times on the shared 4-CPU host vary: v4-only reruns of the 1 MiB root flow ranged 1.7 to 3.9 s, and the spike's 1,000-Route benchmark took 21 ms/op at the assessment and 68 ms/op at load average about 10. Allocations and heap figures reproduce.
- Agent-cost figures are extrapolated from the S1 record and the spike's timing; nobody has measured the cost of a production-quality hand-written parser.
- The v4 suite runner copies WP-33's comparison (events, typed values and `in.json`); the spike's runner compares exact event streams only, which is stricter on markers and flow styles but checks no typed values; typing is the shared `scalar.go`, and typed trees were compared through the WP-33 differential.

## 4. Recommendation

**Choose C2: a hand-written parser for the restricted profile, with no third-party YAML module in production, checked in tests against `go.yaml.in/yaml/v3`. If the user declines the test-only oracle, choose C.**

Why:

1. **A does not converge, and nobody upstream will help.** Four loops confirmed 12, 8, 4 and 5 serious findings; each loop found 3 to 10 new goccy behaviors; the defects are moving into the workaround code itself (60% in the last loop). Fixing the five open findings means more prediction of goccy. goccy has merged nothing in six months, fix PRs for other WP-33 behaviors (#889, #902, #941, #949, #900) sit unreviewed, and two causes of the open findings have no upstream issue at all. Its S1 window closes in 90 days.
2. **B is blocked as published, and its fork-free fallback is weaker than C.** rc.4 to rc.6 retain about 500 B of heap per input byte for a flow sequence at the root, after `- ` or inside a flow sequence (1 MiB root `[1,...]`: about 500 MiB, so the 01 test plan's 256 MiB per 1 MiB fuzz budget fails); JSON-style objects cost 130 to 215 B per byte (4 MiB: 772 MiB). It is a release candidate with an API still changing, it refuses `%YAML 1.2`, it passes 36 fewer suite cases than WP-33, and it refuses about 42 valid streams (29 new against WP-33), many with tabs. It offers no token count and no context inside a document. B2 fixes the cost only by carrying a patched copy, a user-hosted fork or a nested module that needs a layout exception, and nobody has reported the regression upstream. B3 avoids the regression without a fork but refuses 7 more valid suite streams, keeps the `%YAML 1.2`, ctx and token gaps, and sits on an API v4.0.0 will replace. B3 is the fallback if C stops.
3. **C measures best, including on checks that share none of its code.** It passes 335 suite cases (WP-33 315, v4 279) under exact event comparison; its positions equal v4's on 928 of 931 nodes; 332,561 generated inputs against v4 and yaml.v3 left only known libyaml deviation classes; it stayed linear on 10 shapes aimed at its own algorithm. On the 224 rows from goccy findings it departs from YAML 1.2 on none. When a review finds a defect, it is in Ruralz code that states the rule, not in a prediction of a library's behavior. Its time is linear by construction; its memory is the trees', and needs per-document conversion and a limits decision (section 6 item 2).
4. **It keeps the exported signatures.** `Parse`, `Options`, `Encode`, `EncodeJSON` and `FormatOf` stay as promised to WP-37, WP-38, WP-39 and WP-51. `MaxDocumentTokens` keeps its name but changes what it counts, a contract change for the user (section 6 item 1). Its documentation cost is the same ADR-0020 that B needs, with the same research question (5.5), without fork or NOTICE obligations.
5. **Now is the cheapest time.** No binary links a YAML module, and the only callers are two uncommitted S2 test helpers that use API C keeps and whose fixtures parse under the spike.
6. **Why C2 rather than C (changed in this revision).** The first version dismissed a test-only oracle because raw yaml.v3 disagreed on 37,831 of 100,000 generated streams. The devil's-advocate review showed that four known libyaml deviation classes explain every difference over 332,561 inputs, so a filtered v3 is a usable oracle. Without it, once goccy leaves, C's permanent net is the suite plus a generator by the parser's author, for a parser that gets no external scrutiny. v3 is already in `go.mod` through cel-go and already in research, so the oracle adds a direct requirement inside the `go.mod` change C needs anyway, a test-only catalog row and a confinement rule.

The reviews also added B3 as the named fallback, corrected the severities, the scope of v4's retention, C's memory and per-file budget, and the strictness question, and asked for an absolute stop rule and a pessimistic cost. None of these moves the choice off a hand-written parser: B3 is the strongest alternative and still loses on correctness, contracts and API churn, and A's projected cost on the same basis as C's pessimistic case ($320 to $600 for four more loops, estimate) is no lower and ends with a larger goccy layer whose S1 window has closed.

The cost of C is real. Ruralz owns YAML's strict corners, positions and messages for good; the suite runner, generator, v3 differential and fuzz targets become permanent maintenance; no outside user, fuzzing service or advisory channel watches the parser. As YAML 1.2 requires, C refuses shapes that every libyaml-family parser accepts, notably a closing `]` or `}` aligned with its key (8 of 32 style rows), so the user decides strict or lenient before implementation (section 6 item 6). Base cost $120 to $290, pessimistic $280 to $740 (estimate).
